# MLOps - Diabetes dataset

[Link]<https://github.com/juan1639/MLOps_diabetes>


- End-to-end MLOps pipeline built on the **diabetes** dataset.
- Each script is self-contained, independently runnable.
- From raw data ingestion, served, and CI-tested model.

The API is containerised with Docker and deployed automatically to **Render** on every push to `master` (see [CI/CD](#cicd)).

**Stack:** Python 3.11 · scikit-learn · MLflow 2.9+ · Pydantic v2 · FastAPI · Docker · GitHub Actions · GHCR · Render

---

En las versiones actuales de MLflow se recomienda utilizar una **base de datos**, en lugar de **mlruns/**

## Data pipeline

Run from the project root. Each script depends on the output of the previous one.

```bash
python -m src.data.load_data          # → data/raw/diabetes_dataset.csv
python -m src.data.validate_data      # → Simple data validate (raw + incoming)
python -m src.data.preprocess         # → data/processed/train_v1.csv
```

| Script | Input | Output |
|---|---|---|
| `load_data.py` | sklearn API | `data/raw/diabetes_dataset.csv` |
| `validate_data.py` | `data/raw/diabetes_dataset.csv` + `data/incoming/*.csv` | console summary |
| `preprocess.py` | `data/raw/diabetes_dataset.csv` + `data/incoming/*.csv` | `data/processed/train_v1.csv` |

### Adding new data (`data/incoming/`)

To retrain with new labelled rows, add a CSV file to `data/incoming/` and push it:

- Same columns as the raw dataset: `age, sex, bmi, bp, s1, s2, s3, s4, s5, s6, target`.
- **Same scale** as the raw dataset (features already scaled, values around -0.2 … 0.2).
  `validate_data.py` fails if a feature is far outside the raw range (e.g. real ages).
- Files are merged in name order, so a name like `2026-11_new_patients.csv` keeps them sorted.

The train/test split is **stable** (`src/data/split.py`): each row goes to train or
test according to a hash of its values, so adding rows never moves the old ones. That
keeps the champion/challenger comparison fair (see Step 3).

---

### Step 1 — Experiment Tracking

**What you learn:** how to log params, metrics, and model artifacts so every run is
reproducible and comparable.

```bash
python -m src.models.train
```

Trains a `LinearRegression`, `RandomForestRegressor(n_estimators=100)`and a `GradientBoostingRegressor`
on `train_v1.csv`. Each model is logged as a separate run in the
`diabetes-dataset` experiment with metrics `rmse`, `mae`, `r2`.

Each run is also tagged with `dataset_hash` (version of the data) and `split_method`,
and stores `feature_stats.json` (min/max of every feature, used by the API monitoring).

---

### Step 2 — Model Registry

**What you learn:** how to promote the best run into a named, versioned model that
consumers can reference without knowing a run ID.

```bash
python -m src.models.register_model
```

Queries the finished training runs **made with the current data** (same `dataset_hash`;
evaluation runs are ignored), picks the one with the lowest RMSE, registers it as
`diabetes-dataset-model` and gives it the alias **`challenger`**. If that run is already
registered, the existing version is reused instead of creating a duplicate.

**Requires:** Step 1 to have been run at least once.

---

### Step 3 — Model Evaluation

**What you learn:** how to run a formal quality gate, compare a new model against the one
in production (champion vs challenger) and promote it with an alias instead of a stage
transition (MLflow 2.9+).

```bash
python -m src.models.evaluate_model
```

Runs `mlflow.evaluate()` on the current test set for the `challenger` and for the current
`champion` (if any). Quality thresholds:

| Metric | Threshold |
|---|---|
| RMSE | < 60 |
| R² | > 0.44 |

I use these thresholds values considering the results obtained.

| Situation | Result |
|---|---|
| No champion yet, challenger passes the thresholds | challenger → `champion` |
| Challenger passes and its RMSE is not worse than the champion's | challenger → `champion` |
| Challenger is worse, or fails the thresholds | current champion is kept (warning in CI if it failed) |
| Champion trained with another `split_method` | not compared (unfair); challenger only needs the thresholds |
| No model passes the thresholds | exit code 1 → CI deploys nothing |

You can then load the production-ready model anywhere with:

```python
import mlflow
model = mlflow.pyfunc.load_model("models:/diabetes-dataset-model@champion")
```

**Requires:** Step 2 to have been run at least once.

## Serving

The API serves predictions from whichever model version holds the `champion` alias.
Run Steps 1–3 above before starting the server.

### Local

```bash
uvicorn src.api.main:app --reload
# Docs: http://localhost:8000/docs
```

### Endpoints

| Method | Path | Description |
|---|---|---|
| `GET` | `/health` | Liveness check |
| `GET` | `/model-info` | Name, version, alias, run\_id of the loaded model |
| `POST` | `/predict` | Returns `{"prediction": float, "model_version": str}` |

### Monitoring

- Every prediction is logged as one JSON line (`"event": "prediction"`, inputs, output,
  model version), visible in the Render logs.
- If an input is far outside the range seen in training, a `WARNING` is logged
  (`Input out of training range: age`). The prediction is still returned. Since the
  features arrive already scaled by the intermediate backend, this warning usually means
  the values were not scaled as expected.

### Example request

```bash
curl -X POST http://localhost:8000/predict \
  -H "Content-Type: application/json" \
  -d '{
    "age": 0.0,
    "sex": 0.0,
    "bmi": 0.0,
    "bp": 0.0,
    "s1": 0.0,
    "s2": 0.0,
    "s3": 0.0,
    "s4": 0.0,
    "s5": 0.0,
    "s6": 0.0
  }'
```

## CI/CD

Every push to `master` (or a manual run from the **Actions** tab) triggers
`.github/workflows/ci.yml`, which runs the full pipeline in order:

```
ruff → pytest → restore mlruns/ from the deployed image
   → load_data → validate → preprocess → train → register_model → evaluate_model
   → docker build → push to GHCR → deploy on Render
```

Before training, the workflow copies `mlruns/` out of the image that is currently
deployed (`ghcr.io/...:latest`). That brings back the run history and the current
`champion`, so `evaluate_model.py` can compare the new model against it. On the very
first run (no image yet) it starts with an empty store.

If `evaluate_model.py` exits with code 1 (no model passes the quality gate), the workflow
fails and **no image is built or deployed**: the API keeps serving the previous champion.
If the new model is simply not better, the champion is kept and the image is still built
(so code changes are deployed).

> `mlruns/` grows with every run (≈ 3 MB per run: 3 models + evaluations), and it goes
> into the image. The "MLflow store size" step shows its size.

### Why the image is built inside the workflow

`mlruns/` is in `.gitignore`, so it doesn't exist in the repository. The GitHub
Actions runner is a temporary machine: it creates `mlruns/` while training and is
destroyed when the job ends. Building the Docker image in that same job, right after
the quality gate, is what puts the champion model inside the image
(`COPY mlruns/ ./mlruns/`). The next run restores it from that image.

The image is published to GitHub Container Registry with two tags:

| Tag | Use |
|---|---|
| `ghcr.io/juan1639/mlops_diabetes:latest` | The one Render deploys |
| `ghcr.io/juan1639/mlops_diabetes:<commit sha>` | History, to roll back to a previous model |

## Deploy on Render (one-time setup)

1. **Run the workflow once** (push to `master`) so the image exists in GHCR.
2. **Make the image public**: GitHub profile → *Packages* → `mlops_diabetes` →
   *Package settings* → *Change visibility* → **Public**.
   (Or keep it private and add a GitHub token with `read:packages` as registry
   credentials in Render.)
3. In Render: **New** → **Web Service** → **Existing image** →
   `ghcr.io/juan1639/mlops_diabetes:latest`.
   - Instance type: *Free*
   - Health check path: `/health`
   - No need to set the port: Render provides `PORT` and the Dockerfile uses it.
4. Copy the service's **Deploy Hook** URL (*Settings* → *Deploy Hook*).
5. In GitHub: *Settings* → *Secrets and variables* → *Actions* → **New repository
   secret** named `RENDER_DEPLOY_HOOK` with that URL.

From then on, every push to `master` retrains, evaluates and, if the model passes
the gate, redeploys the API automatically.

> On the free plan the service sleeps after a period without traffic, so the
> first request after a while can take some time to respond.
